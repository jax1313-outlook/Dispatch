## Known Windows-only unknowns

These are properties of the target machine that no test in this repository can
establish. Each is a question for Mike, not an assumption made in code:

1. Whether `py.exe` (the Windows Python launcher) is installed, and whether it
   resolves to the same interpreter that has Flask installed. `dispatch.bat`
   prefers `py -3` and falls back to `python`.
2. Whether `powershell.exe` runs `Get-CimInstance Win32_Process` for this user.
   If it does not, the launcher can still see that a process is alive but cannot
   confirm its identity, and will refuse to stop it rather than risk terminating
   the wrong program.
3. Whether `taskkill` and `tasklist` are available and permitted.
4. Whether the `D:` drive and the `DISPATCH_OPERATIONS_ROOT`,
   `DISPATCH_ARCHIVE_ROOT` and `DISPATCH_MEMORY_ROOT` variables are set in the
   session that double-clicks `dispatch.bat`. `setx` values only reach **new**
   windows — see `setup_dispatch_folders.ps1`.
5. Whether Windows Defender or SmartScreen interferes with a detached process
   created from a double-clicked `.bat`.
6. Whether the console code page renders the status block correctly. All launcher
   output is ASCII specifically so that it does, but this is unconfirmed.

## A verification error worth recording

The first liveness check used `ps -p <pid> >/dev/null && echo ALIVE`, which reported the
stopped process as still alive. The process was gone; this `ps` build exits 0 whether or
not the PID matches, so the check was meaningless. Re-checked against `/proc/<pid>` and
`ps aux | grep -c portal/app.py`: old PID dead, new PID alive, zero portal processes after
Stop.

The launcher's own confirmation was correct throughout — it polls the PID and reports what
it finds. The ad-hoc check was the unreliable one. This is precisely the failure mode
Section 4.3 step 16 warns about, hit here in the harness rather than in the product, and it
is why the proof procedure tells Mike to believe the PID rather than the browser.
